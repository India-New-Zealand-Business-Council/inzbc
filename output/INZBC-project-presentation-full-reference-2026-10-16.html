1. The project in one minute

We are developing a digital platform for the India New Zealand Business Council, or INZBC. It brings together trade intelligence, sourced FTA guidance, communications drafting and a refreshed public website. The main engineering challenge is making information useful while keeping evidence, decisions and publication under human control.

Our platform collects potential intelligence, supports assessment, records review and approval, and preserves an audit history. The FTA Explainer retrieves approved source material rather than generating tariff advice. AI helps with scoring, drafting and advisory quality checks, but it cannot grant approval or independently publish an output.

We have built and tested the core application and are improving evaluation, integration and operational readiness. Production launch is still gated, and the remaining deployment and handover work is clearly recorded.

Useful opening sentence: “Our contribution is a governed workflow around information and AI: every important output needs evidence and a recorded human decision.”

2. What problem are we solving?

INZBC needs to turn information about India–New Zealand trade into material that staff and members can use. The project brief describes fragmented information, separate membership systems, website improvement needs and a need for clearer control over organisational knowledge.

4. How the system works

The architecture in plain language

There are three repositories with different responsibilities:

  • inzbc: the platform application, shared API, database, staff interfaces and controls.
  • daily-india-nz-news-agent: the separate collection engine that handles external feeds.
  • inzview: the public website. Earlier documents discuss Wix Studio/Velo; the newer website implementation uses Astro, React and Wix tooling.
Public sources → collection and candidate processing → platform API → PostgreSQL
                                                        ↑
Staff → unified React application → session/role checks → workflow actions
                                                        ↓
                                  source refusal → redaction → model gateway → provider

Public FTA question → corpus retrieval → cited answer / no match / coverage warning
                                        (no LLM call in this retrieval path)

Membership journey → Member Jungle link-out

The public site and staff platform have different trust boundaries. Staff actions use platform sessions and role checks. The public FTA query endpoint is deliberately anonymous. A proposed website/platform boundary ADR explains why staff tools should use the platform origin; its proposal status should not be described as a signed client decision.

One intelligence run

  1. An authorized operator creates and authorizes a run.
  2. Candidate information is captured, deduplicated and associated with sources.
  3. Assessment recommends relevance and signal strength; human verification remains separate.
  4. Selected candidates form a versioned report. A content hash binds the submitted material.
  5. A reviewer records QA. A failed review can return the report for correction.
  6. The appropriate human records the decision and distribution authority.
  7. Delivery is recorded separately; approval does not by itself mean an email was sent.
  8. Audit records preserve the actions and evidence references.

This is a simplified explanation, not the full state-machine specification. The application enforces legal transitions in code and uses database constraints and append-only records for additional protection. An LLM response cannot substitute for a required human gate.

6. The LLM configuration: what to say when asked

Short answer: “The platform gateway defaults to OpenAI gpt-4.1-mini, called from the server through the Responses interface. Configuration is supplied at runtime. The gateway checks the declared data source, applies the approved redaction policy, makes the request and records content-free usage metadata. We are integrating an existing model, not training one.”

The table below describes the platform gateway, not a guarantee that the separate collector uses identical settings. No runtime .env file or secret value was read for this briefing.

What these parameters mean: temperature/top-p affect sampling; token caps constrain response length; timeouts bound waiting at the client layer; retries trade resilience against latency and possible extra cost. Our current code explicitly sets some controls and leaves others to the provider. Choosing sampling settings, output caps or snapshot pinning would be future engineering work requiring validation, not something this document silently changes.

Where AI is used

  • Candidate scoring: recommends NZ, India and member relevance on integer 0–5 scales, signal strength, source confidence and a reason. It does not assign factual verification.
  • Communications drafting: supports newsletter sections, LinkedIn posts, event announcements and member spotlights, with formal/warm/concise tone selections. Output remains a draft.
  • Advisory brief-quality judging: scores NZ relevance, member actionability, evidence support and signal discipline. Any dimension below 3 produces needs_revision in application code.

The quality judge accepts up to 12,000 characters each for the brief and evidence, demands strict scores and reasons, and rejects extra or invented approval fields. It advises the reviewer; it cannot perform QA sign-off, authenticate a source or authorize distribution.

Where AI is deliberately absent

The current FTA answer retrieval path searches the curated corpus. It does not ask an LLM to invent an explanation, tariff or source. Embeddings/pgvector and hybrid retrieval are open engineering ideas, not the current production retrieval mechanism. We have no verified project-specific model training or fine-tuning result to present.

9. Testing and the results we can defend

Automated engineering checks

The current CI covers Python lint/tests with a 90% coverage gate, generated API-type drift, frontend lint/typecheck/tests/build, Storybook compilation, Semgrep, gitleaks, workflow validation, links, Docker build and HTTP smoke tests. Nine jobs passed on PR #429's final head before merge.

The September v1.0 release records 1,188 Python and 410 frontend tests. Those are historical release counts, not a fresh pass count from this briefing. Some local Python runs skip database-dependent tests; those skips must not be described as database coverage.

FTA retrieval evidence

The committed current.json contains 55 questions: 45 answerable and 10 no-match cases. Recorded hit@1, hit@3, mean reciprocal rank and no-match accuracy are all 1.000 on that set.

  • Hit@1: the expected result is ranked first.
  • Hit@3: an expected result appears in the first three.
  • MRR: rewards putting the expected result near the top.
  • No-match accuracy: checks that unanswerable cases remain unmatched.

This is a known development set. It is not proof of 100% real-world accuracy. PR #416 reports 0.800 hit@1 on ten separate synonym questions, compared with 0.500 without the synonym map. That PR is still open; its result was read from the submitted evidence, not independently rerun for this briefing. Its “visitor numbers” no-match and incorrect “economic impact study” result show useful remaining weaknesses. Some reported held-out items were already synonym-map keys, so do not call the entire set perfectly blind. Once questions are examined or used for tuning, fresh questions are needed for another genuinely unseen evaluation.

Live LLM quality evidence

The actual artifact from quality run 38814897919 was downloaded and read. It ran on main with gpt-4.1-mini, using rubric sip-quality-v1 and its pinned fingerprint. All eight synthetic cases met the configured expectations; the report contains failures: [].

Examples: supported specific action scored 5/5/4/5; an unsupported tariff claim scored 1/1/0/1; vague action scored 3/1/3/4. Six cases were flagged for revision; two were not.

This is a real provider result on hand-authored synthetic fixtures. It does not establish real-article calibration, universal injection resistance, independent human agreement or client acceptance. Ordinary PR CI runs offline checks; the live quality workflow is manually triggered and is not a required branch check. No new model call was made for this briefing.

Demonstration checklist

Use a prepared local/demo environment with synthetic data. scripts/platform.ps1 is the platform runner; scripts/demo.ps1 is the smaller FTA-only path. Verify the environment before the presentation rather than assuming the scripts or model account are ready on the day.

  1. Select a seeded run and show that the header and candidate list refer to that same run.
  2. Show source coverage, report selection and a read-only view of recorded decisions/audit.
  3. Demonstrate a refusal or failed gate using a prepared test account/scenario.
  4. Ask the FTA Explainer “wool”; show source attribution, then a prepared unsupported query.
  5. Show a stored synthetic communications draft and its reviewer requirement. If live model access is unavailable, say so and use a clearly labelled saved example.
  6. Show the evaluation report; explain one success and one known failure.

Do not use production credentials, real member data, live sending or a public-site cutover as a presentation demonstration. A recorded delivery in a synthetic walkthrough is not a real send.

13. Likely questions and clear answers

Is this just an AI chatbot? The main application is a workflow, data and control system. AI is used at specific steps; identity, report versions, state transitions and approvals are implemented outside the model.

Why not let AI publish automatically? INZBC needs attributable, source-backed communications. A model can produce a plausible error; the system therefore keeps consequential release decisions with named humans.

Is the FTA Explainer RAG? It retrieves from a sourced knowledge corpus, but the current public answer path does not perform LLM generation. Describe it as curated retrieval. Vector/embedding retrieval is future work.

Why did you choose this model? gpt-4.1-mini is the implemented default. The gateway allows configuration and we now have a bounded quality-evaluation mechanism. We have not established that it is the optimal model through a broad comparative benchmark; model replacement needs evidence.

Did you train a model? What is the training dataset? No project-specific training or fine-tuning is verified. We use existing external models, project prompts, a curated FTA corpus and synthetic regression/evaluation fixtures. The corpus and test fixtures are not a model training dataset.

How do you stop hallucinations? We reduce exposure through sourced retrieval, strict contracts, explicit missing-evidence handling and human review. These do not eliminate every semantic error. The separate FTA question set already contains an incorrect match, which we report rather than hide.

Is the model deterministic? We do not claim that. The gateway sets no explicit temperature, seed or dated model snapshot. Strict parsing constrains accepted structure, not repeated semantic identity.

What happens if the model fails? The gateway has bounded retries and surfaces failure. Missing configuration or malformed output does not become a fabricated recommendation. A failed usage-audit write prevents returning the result and does not trigger another provider call.

How much does it cost? There is no verified total operating bill in this briefing. The gateway records available token usage and either provider-reported USD cost or a labelled estimate using configured rates:

estimated USD = (input tokens × input rate + output tokens × output rate) / 1,000,000

Missing rates/counts mean unknown cost, not zero. Hosting plans, quotas and model prices must be checked when deployment is arranged; earlier free-tier assumptions are not current guarantees.

How does it scale? The design separates collection, web requests and persistent state. That is an architectural starting point, not load-test evidence. We have not demonstrated production concurrency, availability or a capacity/SLA figure for this briefing.

What were the hardest engineering problems? Preserving approval authority across processes, binding decisions to actual report content, enforcing separation of duties, connecting UI state to the correct run, and handling sensitive text before an external call. September fixes included run-ID confusion, wrong-run candidate selection, incorrect content hashing and clock differences between the app and database.

What did each teammate contribute? The documented lanes are Bhanu: technical lead, backend/control platform and shared contracts; Roshan: intelligence, source/data and FTA work; Paras: product experience, frontend and website work. Use PRs and individual worklogs for precise attribution rather than assigning every cross-cutting feature to one person.

What is the next step? Complete the existing evaluation/integration tasks, prepare and verify the hosted environment, record outstanding acceptance/security evidence, and complete recipient handover and recovery verification. Production remains a separate client decision.
